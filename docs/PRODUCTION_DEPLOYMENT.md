# LodgeFlow Premium — Production Deployment

## 1. Server baseline

Recommended minimum for an initial small deployment: 4 vCPU, 8 GB RAM, 80+ GB encrypted SSD, Ubuntu 24.04 LTS or equivalent, Docker Engine + Compose v2, outbound HTTPS/SMTP, external TLS termination, and automated off-server backups. Scale database/storage independently as Lodge/customer volume grows.

Production services are isolated on a private Docker bridge. PostgreSQL and Redis do **not** publish host ports. Nginx publishes only `127.0.0.1:${APP_HTTP_PORT:-8080}` so TLS should terminate in a hardened external proxy/load balancer.

## 2. Secrets and environment

Copy `.env.production.example` → `.env.production` and set every secret. Generate examples:

```bash
python - <<'PY'
import secrets
from cryptography.fernet import Fernet
print('DJANGO_SECRET_KEY='+secrets.token_urlsafe(64))
print('CREDENTIAL_ENCRYPTION_KEYS='+Fernet.generate_key().decode())
PY
openssl rand -base64 36   # PostgreSQL/Redis passwords
```

Keep the credential encryption key history during rotations; removing a key before all encrypted rows are re-encrypted will make older secrets unreadable.

Required production settings include a strong `DJANGO_SECRET_KEY`, `CREDENTIAL_ENCRYPTION_KEYS`, PostgreSQL/Redis secrets, exact `ALLOWED_HOSTS`, HTTPS `CSRF_TRUSTED_ORIGINS`/`CORS_ALLOWED_ORIGINS`, SMTP, private S3-compatible object storage, and a host-side `BACKUP_ENCRYPTION_PASSWORD_FILE`. Provider webhook authenticity is enforced by provider-specific signature/token verification; the webhook URL itself is not treated as a secret. Keep `CLAMAV_REQUIRED=true` when customer uploads are enabled.

## 3. First deployment

```bash
cp .env.production.example .env.production
chmod 600 .env.production
$EDITOR .env.production
./scripts/deploy-production.sh

docker compose --env-file .env.production -f docker-compose.prod.yml run --rm backend \
  python manage.py bootstrap_lodgeflow
```

The deploy script runs Compose validation, image builds, Django `check --deploy`, migration drift detection, migrations, static collection, service startup and health probes. A failed gate aborts deployment.

## 4. TLS and proxy

Expose only HTTPS publicly. Forward `Host`, `X-Forwarded-For`, `X-Real-IP` and `X-Forwarded-Proto=https`. The included inner Nginx routes `/api/` and `/admin/` to Django and everything else to Next.js. Do not expose PostgreSQL, Redis, MinIO console, Mailpit or ClamAV on the public interface.

## 5. Storage and uploads

Production should use a private S3/S3-compatible bucket. Object ACLs remain private; downloads are authorized by Django. Configure bucket encryption, lifecycle rules and versioning according to your retention policy. Upload validation checks filename, extension, MIME/signature, OpenXML structure, archive expansion limits and optional required ClamAV scanning.

## 6. Email

Use an authenticated transactional SMTP provider and verify SPF, DKIM and DMARC for the sending domain. Test officer invitations, password setup, campaigns and scheduled reports before launch.

## 7. Payments

Configure Stripe/PayMongo/Xendit secrets only through **Platform → Credentials**. The application encrypts secrets at rest and does not return them after write. Use each tenant/environment-specific webhook URL generated by LodgeFlow. Configure test-mode credentials first and verify: signature/token validation, duplicate delivery idempotency, amount/currency matching, rejected mismatches, payment-request reconciliation, receipt sequencing and subscription state updates.

## 8. PHP-first multi-currency

New tenants default to PHP. Each Lodge selects enabled currencies and a base currency from Settings. Automatic FX refresh populates reference rates. Every financial posting freezes the applicable original amount, base-currency amount and FX metadata. Manual rate overrides require an authenticated authorized user and are audited. Do not backfill historical transactions using a current rate.

## 9. Backups and recovery

```bash
install -m 600 /dev/null /etc/lodgeflow/backup-passphrase
openssl rand -base64 48 > /etc/lodgeflow/backup-passphrase
export BACKUP_ENCRYPTION_PASSWORD_FILE=/etc/lodgeflow/backup-passphrase
./scripts/backup.sh /secure/offserver/mount
RESTORE_CONFIRM=RESTORE ./scripts/restore.sh /path/to/lodgeflow-YYYYMMDDTHHMMSSZ.backup
```

Each backup is a mode-aware bundle. It contains an AES-256/PBKDF2-encrypted PostgreSQL custom dump, an encrypted local-media tar archive or encrypted S3 object inventory, a database/private-storage sentinel, per-artifact SHA-256 files, and a checksummed manifest. Restore verifies the whole bundle and rejects missing, modified, linked or path-traversing artifacts before the destructive confirmation. Local-media restore rejects unsafe tar members. The final gate verifies the sentinel in both PostgreSQL and private storage, reconciles migrations, and probes `/api/ready/`.

`BACKUP_MEDIA_MODE=auto` detects local versus S3 storage. Local mode is self-contained. S3 mode records complete object inventory evidence and requires versioning/export recovery operated by `BACKUP_S3_RESTORE_EXECUTABLE`; the restore script refuses to continue without that executable. Configure `BACKUP_TRANSFER_EXECUTABLE` to copy the completed bundle to an off-VPS, access-controlled, versioned destination. Both hook variables must be absolute executable paths, not shell snippets. Keep the passphrase outside the repository and primary backup directory.

Install the provided systemd schedule (adapt `/opt/lodgeflow` and the service account if needed):

```bash
sudo install -d -m 700 -o lodgeflow -g lodgeflow /var/lib/lodgeflow-backups
sudo install -d -m 700 /etc/lodgeflow
sudo tee /etc/lodgeflow/backup.env >/dev/null <<'EOF'
BACKUP_ENCRYPTION_PASSWORD_FILE=/etc/lodgeflow/backup-passphrase
BACKUP_MEDIA_MODE=auto
BACKUP_RETENTION_DAYS=35
BACKUP_TRANSFER_EXECUTABLE=/usr/local/sbin/lodgeflow-offsite-transfer
EOF
sudo install -m 644 deploy/lodgeflow-backup.service deploy/lodgeflow-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now lodgeflow-backup.timer
sudo systemctl start lodgeflow-backup.service
sudo systemctl status lodgeflow-backup.service
```

Run a destructive recovery drill in an isolated environment after every storage/provider change and at least quarterly. A bundle existing on disk is not recovery evidence until the drill completes with database, storage checksum, migration and readiness verification.

## 10. Staging E2E gate

Create `.env.staging` from `.env.staging.example`. The staging Compose overlay adds MinIO S3 and Mailpit while retaining PostgreSQL, Redis/Celery/Beat and ClamAV. Run:

```bash
./scripts/staging-e2e.sh
```

The staging overlay provisions PostgreSQL, Redis, Celery, MinIO S3, Mailpit SMTP and ClamAV, runs Django deployment/migration checks, and probes cache, storage, SMTP, malware scanning and worker connectivity. Complete the configured Stripe/PayMongo/Xendit sandbox callback tests before production promotion; those external callbacks require real provider sandbox accounts and are intentionally not simulated as production acceptance.

## 11. Release checklist

- All automated source/domain/release tests green.
- `python manage.py check --deploy --fail-level WARNING` green.
- `python manage.py makemigrations --check --dry-run` reports no changes.
- Migrations apply to a clean DB and an upgrade copy of production.
- `npm run typecheck` and `npm run build` green.
- Compose config/build/health green.
- SMTP, S3 and ClamAV probes green.
- Payment-provider sandbox callbacks green including duplicates/mismatches.
- Tenant isolation/RBAC/MFA smoke tests green.
- Backup + restore drill green.
- Desktop/tablet/mobile accessibility/keyboard smoke checks complete.

## 12. Operations

Monitor HTTP 5xx/latency, worker queue depth, webhook failures/quarantine, SMTP delivery, storage errors, ClamAV availability, database capacity, backup age, TLS expiry and audit anomalies. `scripts/ops-monitor.py` checks external liveness/readiness components, TLS expiry, backup-status age and disk usage; configure `BACKUP_STATUS_FILE`, `BACKUP_MAX_AGE_HOURS`, `DISK_MONITOR_PATH`, `DISK_WARN_PERCENT` and `ALERT_WEBHOOK_URL` on an external monitoring host. Rotate platform secrets under change control. Keep framework/security patches current and run the complete CI/staging gate before promotion.

### Trusted proxy/IP allowlist requirement

`TRUST_PROXY_HEADERS=true` assumes the service on `127.0.0.1:${APP_HTTP_PORT:-8080}` is reachable only from your trusted TLS proxy/load balancer. That outer proxy **must overwrite/sanitize `X-Forwarded-For` and `X-Forwarded-Proto`** rather than blindly preserving client-supplied values. Lodge IP allowlists use the sanitized left-most forwarded client IP in production. If Django/Nginx is ever exposed directly, disable `TRUST_PROXY_HEADERS` or configure a hardened real-IP policy first.
